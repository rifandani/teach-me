Errors you can see: expected errors vs defects

Failures go in the type, bugs go in the Cause, and handling an error removes it from the type.

Your win for this lesson

Define tagged errors, handle one with catchTag and predict exactly which errors are left in E. Also explain why a defect is a different thing from an expected error.

Typed errors are the feature people cite most when they pitch Effect, so they matter most for your verdict. This lesson shows you what the pitch actually buys you, and what it costs.

Warm-up: from earlier lessons

What do the three channels in Effect<A, E, R> mean, and what does never mean in E?

A is the success value, E is the expected errors, and R is the required services. E = never means the effect cannot fail with an expected error. (Lesson 1)

In a plain TypeScript try { … } catch (e) { … }, what type is e, and why is that a problem?

unknown. The signature of the function you called never said what it throws, so the compiler can't tell you which failures exist or whether you handled them. (Lesson 2)

Inside Effect.gen, how do you fail with an error so that TypeScript knows the function stops there?

return yield* new MyError(...). Errors are yieldable, and the return tells TypeScript execution doesn't continue. (Lesson 3)

1. Two kinds of failure

Effect separates two things that plain TypeScript lumps together as “something was thrown”.[1]

Expected errorDefect
What it isA failure that is part of the domain: card declined, user not foundA bug or an impossible state: a null where there can't be one, a broken invariant
Where it livesIn the type, in the E channelNot in the type. It is recorded only in the Cause
How it's madeEffect.fail(e), or yield* new MyError()Effect.die(e), an exception thrown inside Effect.sync or map, or Effect.orDie
Who handles itCallers recover with catchTag or catchUsually nobody in domain code. Log it at the app's boundary

The docs put it plainly: “Defects usually should not be recovered from inside domain logic.” They get handled at boundaries, with tools like Effect.exit, Effect.catchDefect or Effect.catchCause.[2] The split keeps your error types honest. E lists only the failures a caller could reasonably do something about.

A useful test: “Would any caller write a branch for this?” If yes, it's an expected error. If the only sensible reaction is “fix the code or the config”, it's a defect.

2. Tagged errors, and the type that shrinks

An expected error is usually a class made with Data.TaggedError.[3] The string you pass becomes a _tag field, and Effect uses it to tell errors apart:

import { Data, Effect } from "effect"

class NetworkError extends Data.TaggedError("NetworkError")<{ readonly status: number }> {}
class ValidationError extends Data.TaggedError("ValidationError")<{ readonly field: string }> {}

new NetworkError({ status: 503 })._tag  // "NetworkError"

These errors are yieldable. Inside a generator, yield* new NetworkError({ status: 503 }) means the same as Effect.fail(...).[4] Here is the most important idea in this lesson. Handling an error removes it from the type.

Plain TypeScript: guess and check

async function load(): Promise<string> {
  // might throw NetworkError… or ValidationError…
  // …or anything else. The signature doesn't say.
}

try {
  return await load()
} catch (e) {            // e: unknown
  if (e instanceof NetworkError) return "cached"
  throw e                // did we miss a case?
}                        // the compiler can't tell you

Effect: the compiler keeps score

declare const load: Effect.Effect<string, NetworkError | ValidationError>

const handled = load.pipe(
  Effect.catchTag("NetworkError", (e) =>
    Effect.succeed(`cached (status ${e.status})`))
)
// handled: Effect<string, ValidationError>
//                         ^ NetworkError is gone.
//   `e` was typed as NetworkError, so e.status works.

The other error-handling tools work on the same principle:[5]

load.pipe(Effect.catchTags({                       // Effect<string, never>
  NetworkError: (e) => Effect.succeed(`network ${e.status}`),
  ValidationError: (e) => Effect.succeed(`invalid ${e.field}`)
}))
load.pipe(Effect.catch((e) => Effect.succeed(`failed: ${e._tag}`)))  // every expected error → never
load.pipe(Effect.mapError((e) => `wrapped ${e._tag}`))              // Effect<string, string>: transform, don't recover
load.pipe(Effect.orDie)                                               // Effect<string, never>: "can't happen here" → defect

In v4, catchTag also takes an array of tags, as in Effect.catchTag(["NetworkError", "ValidationError"], handler).[6] If you annotate a function's return type as Effect.Effect<string>, that means E = never. The compiler then refuses to build until every expected error is handled, which gives you exhaustive error handling.

Gotcha: tags must be unique

Suppose two different classes both use the tag "NotFound". catchTag("NotFound") can't tell them apart, and nothing warns you.[4] Give tags distinct, specific names, like UserNotFound and OrderNotFound.

There is a second way to define errors: Schema.TaggedError. It builds errors that can be serialized, for example sent over HTTP. The maintainers' own style guide uses it throughout.[7] You'll meet it in lesson 7. Data.TaggedError is all you need for now.

3. Outcomes as data: Result and Exit

Sometimes you don't want to recover. You just want to look at the outcome. Effect.result turns a failure into a value. The new effect can't fail, and it succeeds with a Result:

const program = Effect.gen(function*() {
  const r = yield* Effect.result(parsePort("abc"))   // Result<number, string>
  return Result.match(r, {
    onSuccess: (port) => `port ${port}`,
    onFailure: (err) => `error: ${err}`
  })
})

At the edge, Effect.runPromiseExit gives you an Exit, which is either a success with its value or a failure with its Cause. In v4 a Cause is a flat list, cause.reasons. Each reason is a Fail (expected error), a Die (defect) or an Interrupt. Helpers like Cause.hasDies(cause) check which kinds are present.[8] This is how you can tell that an error was a bug rather than a domain failure, even after the fact.

Adoption lens: add to your ledger

  • Pro: a function's failure modes are part of its signature, and the compiler checks them. Handling an error removes it from the type, and E = never proves you handled everything.
  • Pro: bugs (defects) stay out of your domain error types, so E doesn't fill up with “anything could happen” noise.
  • Cost: you write an error class for each failure. You also have to wrap throwing or rejecting libraries at the boundary (Effect.try, Effect.tryPromise), or their exceptions show up as defects.
  • Cost: your team has to agree on what is “expected” and what is a defect, and pick Data or Schema errors. These are design decisions, not mechanical ones.

Check yourself

Answer from memory before scrolling back up.

1. load is Effect<string, NetworkError | ValidationError>. After .pipe(Effect.catchTag("NetworkError", () => Effect.succeed("cached"))), what is in E?

  1. catchTag handled NetworkError, so it was removed from the union.
  2. That's backwards. The tag you catch is the one that disappears.
  3. catchTag recovers. The handler's effect replaces the failure, so the handled error leaves the type.
  4. catchTag handles one tag (or a listed set). Effect.catch is the one that handles every expected error.

2. Effect.sync(() => JSON.parse(text)) runs with invalid text. What happens?

  1. The function given to Effect.sync must not throw. If it does, that's a defect. Use Effect.try to get a typed error instead.
  2. Effect.sync has E = never. Only Effect.try, with a catch mapping, puts the exception into E.
  3. Effect captures the exception and records it in the Cause as a Die.
  4. Nothing is swallowed. The effect fails, and the failure is recorded as a defect.

3. Which of these can recover from a defect?

  1. Defects aren't in E, so only the defect- or Cause-level tools (catchDefect, catchCause) see them.
  2. Effect.catch handles every expected error, the ones in E. Defects bypass it.
  3. "Die" is the tag of a Cause reason, not of an error in E. catchTag only sees E.
  4. mapError transforms errors in E. It never sees defects.

4. Two different error classes both use the tag "NotFound". What happens?

  1. The docs warn that tags must be unique. Matching is by the _tag string alone.
  2. There's no such check. That's exactly why the docs call this out as a gotcha.
  3. Nothing checks tags at runtime either. The bug stays silent.
  4. The tag is exactly the string you pass. Effect never renames it.
