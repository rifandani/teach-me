Building programs: gen, pipe and fn

Wrap the code you already have, then sequence it like async/await.

Your win for this lesson

Turn plain TypeScript, including throwing code, Promises and async functions, into Effects. Then chain them with Effect.gen, pipe and Effect.fn.

Warm-up: recall before you read

Answer each one in your head first, then open it to check.

What are the three channels of Effect<A, E, R>, and what does never in the E slot mean?

Success (A), error (E) and requirements (R). E = never means the Effect cannot fail with an expected error. (Lesson 1)

Why does Effect.sync(() => console.log("hi")) print nothing when you define it?

An Effect is a lazy description, a recipe. The function only runs when the Effect is run, and it runs again on every run. (Lesson 1)

Name one thing an Effect can do that a Promise can't.

It can be interrupted. For example, Effect.timeout actually stops the work and runs its cleanup, whereas a Promise keeps running. It can also be re-run or retried, because it is still a recipe. (Lesson 2)

Adopting Effect never starts from a blank page. You have JSON parsing, fetch calls and async functions already. This lesson covers the small toolkit for wrapping that code and gluing the pieces together. It is most of what day-to-day Effect code looks like.

1. Wrap existing code: pick a constructor

Every Effect starts from a constructor. Choose one by answering two questions: is the code sync or async, and can it fail?[1]

You have…UseResulting type
a value alreadyEffect.succeed(a)Effect<A>
an expected failureEffect.fail(e)Effect<never, E>
sync code that won't throwEffect.sync(() => …)Effect<A>
sync code that may throwEffect.try({ try, catch })Effect<A, E>
a Promise that may rejectEffect.tryPromise({ try, catch })[2]Effect<A, E>
a Promise that never rejectsEffect.promise(() => p)Effect<A>

The catch function is where an untyped unknown exception becomes a typed error that you name:

class ParseError extends Data.TaggedError("ParseError")<{ readonly cause: unknown }> {}

const parse = (input: string) =>
  Effect.try({
    try: () => JSON.parse(input) as unknown,
    catch: (cause) => new ParseError({ cause })
  })                                       // Effect<unknown, ParseError>
If code inside Effect.sync throws anyway, the error is not lost. It becomes a defect, an unexpected error that is kept out of E. Lesson 4 covers defects.

Remember that constructors are lazy too. Effect.tryPromise takes a function returning a Promise, not the Promise itself. That lets the Effect start the work each time it runs, instead of once when you define it.

2. Effect.gen: async/await for Effects

Once you have a few Effects, you sequence them. The most readable way is a generator. yield* plays the role of await: it runs an Effect and gives you its success value.[3]

Plain TypeScript: async/await

async function greetUser(id: number) {
  const profile = await fetchProfile(id)
  if (profile.banned) {
    throw new Error("banned")   // invisible in the type
  }
  return `Hello, ${profile.name}!`
}
// Promise<string>: what can fail? unknown

Effect: Effect.gen + yield*

const greetUser = (id: number) =>
  Effect.gen(function*() {
    const profile = yield* loadProfile(id)
    if (profile.banned) {
      return yield* new Banned({ id })   // fail
    }
    return `Hello, ${profile.name}!`
  })
// Effect<string, FetchError | Banned, never>

The shape of the code is the same, but the type is honest. Both the FetchError from loadProfile and the new Banned error show up in E automatically.

To fail inside a generator, yield* a tagged error. Write it as return yield* new MyError(…). The maintainers' style guide asks for the return “to ensure typescript understands that the function will not continue executing”.[5]

3. Pipelines: map, flatMap, tap, andThen

The other style is a pipeline. Every Effect has a .pipe(…) method, and there is a standalone pipe(value, f, g) as well. Each step takes the previous Effect and returns a new one.[4]

const half = (n: number) =>
  n % 2 === 0 ? Effect.succeed(n / 2) : Effect.fail(`odd: ${n}`)

const program = Effect.succeed(10).pipe(
  Effect.map((n) => n * 2),                     // plain function: 10 → 20
  Effect.flatMap(half),                         // function returning an Effect: 20 → 10
  Effect.tap((n) => Effect.log(`got ${n}`)),    // side effect, keeps the value
  Effect.andThen((n) => Effect.succeed(n + 1))  // run the next Effect: 10 → 11
)                                               // Effect<number, string, never>

The rule of thumb: use map when your function returns a plain value, and flatMap when it returns another Effect. tap runs an Effect for its side effect, such as logging, and passes the original value through.

v3 gotcha: andThen and tap are stricter in v4

In v3, Effect.andThen and Effect.tap also accepted plain values, plain-returning functions and Promises. In v4 they accept only an Effect, or a function returning an Effect.[6] So Effect.andThen((n) => n + 1) is a type error, and Effect.tap((n) => console.log(n)) is a type error that also crashes at runtime with “Not a valid effect”. Use Effect.map for pure transforms and Effect.tap((n) => Effect.log(n)) for logging. The migration guide does not call this change out, so expect older tutorials and LLM answers to get it wrong.

4. Effect.fn: reusable functions

A function whose body is a generator is so common that Effect has a constructor for it. Effect.fn("name") also gives each call a named tracing span, which you'll see in lesson 7.

const withdraw = Effect.fn("withdraw")(function*(balance: number, amount: number) {
  if (amount <= 0 || amount > balance) {
    return yield* new InvalidAmount({ amount })
  }
  return balance - amount
})                       // (balance, amount) => Effect<number, InvalidAmount, never>

const withdrawOrZero = Effect.fn("withdrawOrZero")(
  function*(balance: number, amount: number) { return yield* withdraw(balance, amount) },
  Effect.catchTag("InvalidAmount", () => Effect.succeed(0))   // extra args = pipeline steps
)

The maintainers' style guide (LLMS.md) gives three rules:[5]

  • “Prefer Effect.gen for inline Effect code. For reusable functions, prefer Effect.fn("name") when tracing is useful and Effect.fnUntraced when it is not.”
  • “Avoid functions that only wrap and return Effect.gen.”
  • “Do not use .pipe with Effect.fn.” Pass extra steps such as catchTag as extra arguments instead, as shown above.

Sharp edge: ternaries that return different Effects

A function like (id) => id === 1 ? Effect.succeed(user) : Effect.fail(new NotFound()) infers a union of two Effect types rather than one Effect<User, NotFound>. That can break the next .pipe(Effect.catchTag(…)). The fix is to annotate the return type, (id): Effect.Effect<User, NotFound> => …, or to write the body with Effect.gen.

Adoption lens: add to your ledger

  • Pro: you can adopt incrementally. Wrapping an existing Promise or throwing function is one constructor, so you don't have to rewrite your libraries.
  • Pro: Effect.gen reads almost like async/await, so a reviewer who doesn't know Effect can still follow the logic.
  • Cost: there are two styles (generators and pipelines) and several look-alike combinators. A team needs a shared convention, and the maintainers' LLMS.md is a good starting point.
  • Cost: API churn between majors, such as andThen/tap, means older tutorials and LLM output need checking against v4.

Check yourself

Answer from memory before scrolling back up.

1. Your code calls JSON.parse, which throws on bad input. Which constructor fits?

  1. Effect.try is for sync code that may throw, and catch turns the exception into a typed error.
  2. Effect.sync assumes the code won't throw. If it does, you get a defect, not a typed error.
  3. JSON.parse is synchronous, and Effect.promise is for Promises that never reject.
  4. The argument is evaluated immediately, so the throw happens before any Effect exists.

2. Inside Effect.gen, what does const user = yield* findUser(1) do?

  1. yield* works like await. If findUser fails, the generator stops and its error moves into E.
  2. That is what you'd get without yield*. With yield* you get the unwrapped value.
  3. Running work in the background is forking, covered in lesson 6. yield* waits for the result.
  4. No Promise is involved. yield* sequences Effects directly.

3. In v4, what's wrong with Effect.tap((n) => console.log(n))?

  1. In v4, tap and andThen only accept Effects. Write Effect.tap((n) => Effect.log(n)).
  2. tap still exists. It just requires the callback to return an Effect.
  3. That was true in v3. In v4 this is a type error and also crashes at runtime.
  4. console.log is synchronous. The problem is that it returns undefined, not an Effect.

4. Why write Effect.fn("withdraw")(function*(…) {…}) instead of a function that returns Effect.gen?

  1. That is the main reason the maintainers recommend it for reusable functions. The behaviour is otherwise the same.
  2. Calling it returns a lazy Effect, just like Effect.gen does.
  3. Errors stay in E. The withdraw example's type still has InvalidAmount.
  4. The body is still a generator, and you still use yield*.
