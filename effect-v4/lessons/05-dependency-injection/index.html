Dependency injection: services and Layers

Put the requirements channel to work. Your code names what it needs, and the compiler makes sure someone provides it.

Your win for this lesson

Define a service and use it from business logic. Then wire a real and a test implementation with Layers, and run the same code against both.

Warm-up: recall before you read

Answer each one in your head first, then open it to check.

Lesson 1: what does R = never mean, and why do the run* functions insist on it?

It means the Effect needs no services. A runner can only cook a recipe once every ingredient is supplied, so you must provide every requirement first. That is exactly what this lesson is about.

Lesson 3: inside Effect.gen, what does yield* do?

It works like await: it runs the inner Effect and hands you its success value. If the inner Effect fails, the generator stops there and the failure flows out. Its error and requirements are added to the outer Effect's type.

Lesson 4: what happens to the error channel after Effect.catchTag("NotFound", …)?

NotFound is removed from E. Handling a tagged error shows up in the type. Providing a service does the same for R.

1. Why dependency injection at all?

Business logic needs things such as a database, a mailer or a clock. In plain TypeScript you usually import them as module-level singletons. That is convenient until you want to test, or run the same logic with a different database. The Effect docs put the problem bluntly: a TypeScript signature “doesn't tell you what can fail, what dependencies it needs, or whether it can be safely retried”.[1]

Plain TypeScript: hidden imports

// userService.ts
import { db } from "./db"         // global singleton
import { mailer } from "./mailer" // another one

export async function signUp(email: string) {
  if (await db.exists(email)) throw new Error("taken")
  await db.insert(email)
  await mailer.send(email, "Welcome!")
}
// signUp(email: string): Promise<void>
// Nothing here says "needs a db and a mailer".

// userService.test.ts
jest.mock("./db")     // patch modules by file path
jest.mock("./mailer") // and hope you got them all

Effect: requirements in the type

const signUp = Effect.fn("signUp")(function*(email: string) {
  const repo = yield* UserRepo   // ask for a service…
  const mailer = yield* Mailer   // …and it lands in R
  if (yield* repo.exists(email)) {
    return yield* new EmailTaken({ email })
  }
  yield* repo.insert(email)
  yield* mailer.send(email, "Welcome!")
})
// (email) => Effect<void, EmailTaken, UserRepo | Mailer>

// In a test: hand it different implementations.
signUp("ada@example.com").pipe(Effect.provide(testLayer))
// Forget one, and it does not compile.

You could do constructor injection by hand in plain TypeScript: pass db and mailer as parameters. That works, but you have to thread them through every function between main and signUp. The requirements channel threads them for you. Each yield* Service adds that service to R, the types propagate up through every caller, and the program can't run until R is never.

2. Defining and using a service

A service is an interface your code depends on. In v4 there is exactly one way to define one: Context.Service.[2]

import { Context, Effect } from "effect"

class Mailer extends Context.Service<Mailer, {
  readonly send: (to: string, body: string) => Effect.Effect<void>
}>()("app/Mailer") {}

That odd <…>()(…) double call is a common TypeScript trick. The first call takes only the type parameters, and the call it returns takes the runtime value.[3] The line has three parts:

Mailer
Self: the service key
The class itself. You yield* it, and it is the name that shows up in R.
{ send }
Shape
The interface. Any implementation must match it.
"app/Mailer"
Id
The runtime identity. Two services with the same id string share the same slot, so keep ids unique.[3]

Using a service: const mailer = yield* Mailer inside a generator gives you the implementation, and adds Mailer to R. The migration guide says to prefer yield* over the alternative Mailer.use(m => …) “in most cases”.[2]

Providing one implementation directly is what you did in lesson 1. Mailer.of({...}) is a typed helper for building that implementation:

const runnable = signUp("ada@example.com").pipe(
  Effect.provideService(Mailer, Mailer.of({ send: (to) => Effect.log(`mail to ${to}`) }))
) // Mailer is gone from R; UserRepo is still required
provideService is fine for one service with no setup. As soon as an implementation needs config, a connection or other services, reach for a Layer.

3. Layers: recipes for building services

Real implementations have their own needs. A mailer needs SMTP settings, and a repository needs a connection pool. A Layer is a recipe that builds services, and like an Effect its type has three parts: Layer<ROut, E, RIn>.[4]

ROut
What it builds
The services this layer provides.
E
How building can fail
For example, the connection was refused.
RIn
What building needs
Other services required to build it.
class SmtpConfig extends Context.Service<SmtpConfig, { readonly host: string }>()("app/SmtpConfig") {
  static readonly layer = Layer.succeed(SmtpConfig, { host: "smtp.example.com" }) // from a plain value
}

class Mailer extends Context.Service<Mailer, {
  readonly send: (to: string, body: string) => Effect.Effect<void>
}>()("app/Mailer") {
  static readonly layer = Layer.effect(          // Layer<Mailer, never, SmtpConfig>
    Mailer,
    Effect.gen(function*() {                     // build with an Effect
      const config = yield* SmtpConfig           // the dependency is read HERE, once…
      return Mailer.of({
        send: (to, body) => Effect.log(`[${config.host}] ${to}: ${body}`) // …so send has R = never
      })
    })
  )
}

Two conventions are on show here. First, the layer lives on the class as static layer; v4 names layers layer, layerTest and so on.[2] Second, service methods keep R = never. The docs call the alternative “requirement leakage”: if send itself required SmtpConfig, every caller of Mailer would suddenly need to know about SMTP. Dependencies belong to the layer, not to the methods.[4]

Composing layers

Three combinators do almost all the wiring:[4]

SmtpConfig.layer ─provide──────▶ Mailer.layer   ⇒  Layer<Mailer>               SmtpConfig fed in, hidden
SmtpConfig.layer ─provideMerge─▶ Mailer.layer   ⇒  Layer<Mailer | SmtpConfig>  fed in, and kept in the output
UserRepo.layer   ＋  MailerLive    (merge)       ⇒  Layer<UserRepo | Mailer>    side by side, nothing fed
You writeMeaning
Mailer.layer.pipe(Layer.provide(SmtpConfig.layer))Satisfy Mailer's RIn and hide the dependency. This is the usual choice.
Mailer.layer.pipe(Layer.provideMerge(SmtpConfig.layer))Satisfy it and keep SmtpConfig in the output, for when someone else needs it too (often a test).
Layer.merge(UserRepo.layer, MailerLive)Combine independent layers into one.

Then you provide the whole graph once, at the edge: program.pipe(Effect.provide(appLayer)). New in v4, layers are memoized even across separate Effect.provide calls, but the guide still recommends composing first and providing once.[5]

4. Testing is just swapping a layer

Since signUp only knows the Mailer interface, a test can give it a fake that records what was sent. That fake is just another layer:

class Outbox extends Context.Service<Outbox, Ref.Ref<ReadonlyArray<string>>>()("test/Outbox") {
  static readonly layer = Layer.effect(Outbox, Ref.make<ReadonlyArray<string>>([]))
}

const MailerTest = Layer.effect(Mailer, Effect.gen(function*() {
  const outbox = yield* Outbox
  return Mailer.of({ send: (to) => Ref.update(outbox, (all) => [...all, to]) })
})).pipe(Layer.provideMerge(Outbox.layer))   // keep Outbox visible so the test can read it

const test = Effect.gen(function*() {
  yield* signUp("ada@example.com")            // the exact same business logic
  return yield* Ref.get(yield* Outbox)        // ["ada@example.com"]
}).pipe(Effect.provide(Layer.merge(UserRepo.layer, MailerTest)))

No module patching and no file paths. The test layer's type tells you exactly what it replaces. With @effect/vitest, the same idea reads it.effect("…", () => program.pipe(Effect.provide(TestLayer))).[6]

Reading older tutorials? v3 vs v4

  • Context.Tag("X")<X, Shape>(), Context.GenericTag, Effect.Tag and Effect.Service are all v3. v4 replaced every one of them with Context.Service, and the order flipped: type parameters first, id second.[2]
  • v3's Effect.Service generated a .Default layer and took a dependencies option. In v4 you can still store a constructor with Context.Service<X>()("id", { make }), but you write static layer = Layer.effect(this, this.make) yourself.
  • Static accessors like Mailer.send(...) are gone. Use yield* Mailer. Layer.scoped is now just Layer.effect, and FooLive / Foo.Default became Foo.layer.
  • Early v4 betas called this ServiceMap.Service. It was renamed to Context in 4.0.0-beta.44, so beta-era blog posts may show it.[7]

Adoption lens: add to your ledger

  • Pro: dependencies are visible in the type, and the compiler refuses to run a program with one missing. No DI container, decorators or reflection are involved.
  • Pro: tests swap whole implementations by providing a different layer, with no module mocking. Setup such as config and connections lives in one place.
  • Cost: ceremony. Each dependency becomes a class, a shape and a layer, which is more up-front typing than import { db }.
  • Cost: when a service is missing deep in a layer graph, the type errors can be long. The Effect language service (@effect/tsgo) flags some of these leaks for you.[8]

Check yourself

Answer from memory before scrolling back up.

1. In class Mailer extends Context.Service<Mailer, Shape>()("app/Mailer") {}, what is "app/Mailer" for?

  1. The id string is the service's identity at runtime. Reusing it for another service makes them share a slot.
  2. Effect never looks at files. You provide implementations explicitly with layers.
  3. It does matter at runtime: it is the key the service is stored and found under.
  4. Nothing is auto-imported. The string is just a unique key.

2. Mailer.layer is Layer<Mailer, never, SmtpConfig>. What is Mailer.layer.pipe(Layer.provide(SmtpConfig.layer))?

  1. provide feeds the dependency in and removes it from both the input and the output.
  2. That is what provideMerge does. provide hides the dependency.
  3. The SmtpConfig requirement has just been satisfied, so RIn becomes never.
  4. Layers depending on other layers is the whole point; provide is how you connect them.

3. A test must read the fake Outbox after running signUp. How should MailerTest get its Outbox?

  1. The test can only yield* Outbox if the layer still provides it.
  2. Hidden means the test can't reach it. You'd get "Service not found".
  3. merge puts layers side by side without feeding one into the other, so MailerTest would still need an Outbox.
  4. Tests read services from layers all the time, with yield*.

4. Mailer needs SmtpConfig. Where should it ask for it?

  1. That keeps send at R = never, so Mailer's users don't need to know about SMTP.
  2. That is requirement leakage: an implementation detail spreads to every caller's type.
  3. That is the hidden singleton problem from section 1, back again.
  4. That is hand-threading; the requirements channel and layers exist to avoid it.
