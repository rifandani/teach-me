Why not plain TypeScript?

The problems Effect solves, and what it costs you.

Your win for this lesson

Name four concrete problems plain TypeScript leaves to you, and the Effect answer to each. Then write the first honest draft of your adoption ledger, with the costs included.

Warm-up: from lesson 1

Answer each one in your head before you open it.

Why does defining Effect.sync(() => console.log("hi")) print nothing?

An Effect is a lazy description, a recipe. The function only runs when the Effect is run, and it runs again on every run.

What are the three channels of Effect<A, E, R>, in order?

Success (A), error (E, the expected errors), and requirements (R, the services it needs). E and R default to never.

What must be true of R before you can call Effect.runPromise?

R must be never. You provide every required service first, then run at the edge.

1. TypeScript describes your data, not your programs

The official pitch fits in one sentence: “TypeScript is excellent at describing your data, but it says almost nothing about your programs: a function's signature doesn't tell you what can fail, what dependencies it needs, or whether it can be safely retried, timed out, or interrupted.”[1] The rest of this lesson tests that claim against four everyday pains. For each one, you get a preview of the Effect answer. The details come in later lessons.

Pain 1: failures are invisible

Plain TypeScript

// The signature says `number`. It lies.
const divide = (a: number, b: number): number => {
  if (b === 0) throw new Error("Cannot divide by zero")
  return a / b
}

try {
  divide(1, 0)
} catch (e) {
  // e is `unknown`. You had to *remember* to catch,
  // and you have to guess what you caught.
}

Effect

class DivideByZero extends Data.TaggedError("DivideByZero")<{}> {}

const divide = (a: number, b: number): Effect.Effect<number, DivideByZero> =>
  b === 0 ? Effect.fail(new DivideByZero()) : Effect.succeed(a / b)

const safe = divide(1, 0).pipe(
  Effect.catchTag("DivideByZero", () => Effect.succeed(Infinity))
)  // Effect<number, never, never>: handled, and the type shows it

The docs call this Effect's “major unique insight”: using the type system to track errors and context, not only success values.[2] When you handle DivideByZero, it disappears from the error channel. If you forget, the compiler still shows it. Lesson 4 covers expected errors and defects.

Pain 2: dependencies are hidden

Plain TypeScript (sketch)

import { db } from "./db"   // module-level singleton

export async function getUser(id: string): Promise<User> {
  return db.findUser(id)     // the signature never mentions db
}

// To test it: mock the module, or thread `db`
// through every function by hand.

Effect (sketch)

const getUser = (id: string) =>
  Effect.gen(function*() {
    const db = yield* Database   // asking puts Database in R
    return yield* db.findUser(id)
  })  // Effect<User, UserNotFound, Database>

// Tests provide a fake Database.
// Forget to provide one and it won't compile.

You saw a small version of this in lesson 1, where Clock sat in R until you provided it. Lesson 5 covers services and Layers.

2. Promises start eagerly and can't be stopped

Pain 3: no cancellation, no cleanup

A Promise is already running when you get it, and the language gives you no way to stop it. The common “timeout” pattern, Promise.race, only stops waiting. The losing work keeps running.[3] Promise.all is similar. It rejects as soon as one input rejects, but the others carry on, and it has no concurrency limit, because the work started before you called it.[4]

Plain TypeScript

const timeout = (ms: number) =>
  new Promise<never>((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms))

const report = await Promise.race([
  buildReport(),   // still running after the race is lost
  timeout(100)
]).catch(() => "fallback")

Effect

const slowTask = Effect.gen(function*() {
  yield* Effect.log("task started")
  yield* Effect.sleep("2 seconds")
  yield* Effect.log("task finished") // never printed
  return "result"
}).pipe(Effect.onInterrupt(() => Effect.log("cleanup ran")))

const program = slowTask.pipe(
  Effect.timeout("100 millis"),     // interrupts slowTask
  Effect.catchTag("TimeoutError", () => Effect.succeed("fallback"))
)
await Effect.runPromise(program)    // "fallback", after ~100ms

That Effect code was run against effect@4.0.0 for this course.[5] When the timeout fires, slowTask is interrupted: it stops, and its cleanup still runs. The same applies to Effect.all. You can cap it with { concurrency: n }, and when one task fails, its siblings are interrupted. Lesson 6 covers resources and concurrency.

To be fair, plain TS can cancel some work with AbortController. You have to thread the signal through every call by hand, though, and nothing in the types reminds you to.

Pain 4: hand-written retry loops

Plain TypeScript

async function withRetry<T>(fn: () => Promise<T>, times: number) {
  let last: unknown
  for (let i = 0; i <= times; i++) {
    try { return await fn() } catch (e) { last = e }
  }
  throw last
}
// Backoff? Jitter? Only retry some errors? More code.

Effect

callApi.pipe(Effect.retry({ times: 3 }))

// Exponential backoff, at most 5 retries:
callApi.pipe(Effect.retry(
  Schedule.max([Schedule.exponential("10 millis"), Schedule.recurs(5)])
))

Retry works because an Effect is a recipe: you can cook it again. A Promise has already been cooked, which is why withRetry has to take a function that makes a fresh Promise. The docs put it this way: “Because programs are values, they compose: retries, timeouts, concurrency, resource handling, and tracing are operators you apply, not architectures you rebuild.”[1]

3. What it costs

A fair verdict needs the other column too. These costs come from the project's own pages and from what this course's research ran into:

  • Learning curve. The API surface is large. The official Myths page admits it and suggests starting with “10–20 core functions”.[6]
  • Bundle size. About 6–7 kB gzipped for a minimal program, about 15 kB with Schema.[7][8] That is small, but not zero.
  • Version churn. v4 renamed many v3 APIs, so older tutorials, Stack Overflow answers and LLM output are often wrong for v4. On the plus side, 4.x is a long-term-support release, supported until at least Sept 2029.[7]
  • Unstable edges. Core modules follow strict semver. HTTP, SQL, AI, CLI, RPC and similar modules are marked unstable and can break in minor releases.[8]
  • Type-inference sharp edges. If the branches of a ternary return different Effects, TypeScript infers a union of Effect types, which breaks the next .pipe(...). The fix is to annotate the return type, as divide does above.
  • “Effect all the way down” (community opinion, not an official source). Effect code composes best with other Effect code, so it tends to spread through a codebase. The maintainers' own advice is to cross over at the edges with runPromise or ManagedRuntime.[9] Lesson 8 tests this.

What about speed? The Myths page says the “500x slower” claim “only applies when measuring trivial operations like 1 + 1”. Effect is “an app-level coordination library rather than a low-level operation wrapper.”[6]

Reading older tutorials? v3 vs v4

The official Myths page has not been updated for v4 yet. Its starter list still shows Effect.catchAll (now Effect.catch) and the Either module (now Result), and its ~25 kB bundle figure is from v3.[10] Read it for the arguments, not the code.

Adoption lens: your ledger, first draft

  • Pro: failures and dependencies appear in signatures, so the compiler tracks them for you (pains 1 and 2).
  • Pro: timeout, retry, concurrency limits and cancellation are operators you add, not code you write (pains 3 and 4).
  • Cost: a real learning curve, plus v3-era material that misleads you, for your whole team.
  • Cost: about 6–7 kB of bundle, and unstable APIs outside the core.
  • Open question: how far does Effect spread into a codebase? Keep an eye on this through lesson 8.

Check yourself

Answer from memory before scrolling back up.

1. A function is typed getUser(id: string): Promise<User>. What does its signature tell you about failure?

  1. Promise has no error type parameter, so a catch gives you unknown.
  2. JavaScript lets you throw any value, and TypeScript doesn't track what a function throws.
  3. Promises can reject. The type just doesn't say so.
  4. Nothing in the signature says that. You'd have to read the body to find out.

2. You write Promise.race([buildReport(), timeout(100)]) and the timeout wins. What happens to buildReport()?

  1. Promise.race only stops waiting. The losing Promise carries on.
  2. Promises have no built-in cancellation, and race doesn't add any.
  3. A Promise runs once. It never restarts.
  4. The timeout rejects its own Promise. Nothing is thrown into buildReport.

3. slowTask.pipe(Effect.timeout("100 millis")): what happens to slowTask when time runs out?

  1. Effect.timeout interrupts the work and fails with a TimeoutError. onInterrupt handlers run.
  2. That is the Promise.race behaviour. Effect interrupts the timed-out work.
  3. It doesn't get to finish. It is stopped at the 100ms mark.
  4. Interruption stops the work. A later run starts the recipe fresh.

4. Which of these is a real cost of adopting Effect v4?

  1. v4 renamed many APIs, so older material is often wrong for v4.
  2. A minimal program is about 6–7 kB gzipped, and about 15 kB with Schema.
  3. You call it from plain code at the edges with runPromise or ManagedRuntime.
  4. Effect is a library. It uses the normal TypeScript compiler (5.9+, with 7 recommended).
