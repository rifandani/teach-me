1. Schema: one definition, three jobs

Data that comes from outside your program (request bodies, JSON files, environment variables) arrives as unknown. In plain TypeScript you usually write the type and a validation function separately, and nothing makes them stay in sync. The maintainers' own guide is blunt about it: “All validation and domain modeling in Effect is done with Schema.”[1] In v4 it ships inside the core package, as import { Schema } from "effect".[2]

Plain TypeScript: two things to keep in sync

type User = {
  id: number
  name: string
  role: "admin" | "member"
}

function isUser(u: unknown): u is User {
  const x = u as any
  return Number.isInteger(x?.id)
    && typeof x?.name === "string" && x.name.length > 0
    && (x?.role === "admin" || x?.role === "member")
}
// Add a field to the type, forget the guard:
// it still compiles. And the guard says "no",
// not *why*.

Effect: the schema is the single source

import { Schema } from "effect"

const User = Schema.Struct({
  id: Schema.Int,
  name: Schema.String.check(Schema.isMinLength(1)),
  role: Schema.Literals(["admin", "member"])
})

type User = typeof User.Type
// { readonly id: number; readonly name: string;
//   readonly role: "admin" | "member" }

// The validator and decoder come from the same
// value, so they can't drift from the type.

That one value gives you three things: a type (typeof User.Type), a validator, and a decoder that turns unknown input into a typed value.[3] You choose how a failure should reach you:

// Throws on bad input. Fine in a script or a test.
const ada = Schema.decodeUnknownSync(User)({ id: 1, name: "Ada", role: "admin" })

// Returns Effect<User, SchemaError>. The failure is an expected error, so catchTag works.
const program = Schema.decodeUnknownEffect(User)({ id: "1", name: "", role: "owner" }).pipe(
  Effect.catchTag("SchemaError", (e) => Effect.succeed(`invalid: ${e.message}`))
) // → 'invalid: Expected number\n  at ["id"]'

// Parse a JSON string and decode it in one step
Schema.decodeUnknownSync(Schema.fromJsonString(User))('{"id":2,"name":"Lin","role":"member"}')

Look at the middle example. SchemaError is a tagged error, so it shows up in E and you handle it with the same catchTag you learned in lesson 4. Invalid input doesn't need a separate error-handling style.

Lesson 4 also mentioned Schema.TaggedError. Now you can see why it exists: the error's fields are described by a schema, so the error can be validated and serialized, for example to send it over HTTP or RPC. The maintainers' examples use it throughout.[4]

class UserNotFound extends Schema.TaggedError<UserNotFound>()("UserNotFound", {
  id: Schema.Int
}) {}   // yieldable, catchable with catchTag, and a real Error subclass
One gotcha: in v4, Schema.Date means a Date object. To accept an ISO string like "2026-10-01", use Schema.DateFromString. The migration guide warns that old code “can still type-check after upgrading while no longer accepting the same input”.[5]

Reading older tutorials? Schema v3 vs v4

  • Schema.Literal("a", "b") → Schema.Literals(["a", "b"]). Arguments that used to be a list are now arrays: Union(A, B) → Union([A, B]).
  • Schema.decodeUnknown → Schema.decodeUnknownEffect; decodeUnknownEither → decodeUnknownExit.
  • Schema.parseJson(S) → Schema.fromJsonString(S).
  • Refinements gained an is prefix and go through .check: minLength(1) → .check(Schema.isMinLength(1)), int() → .check(Schema.isInt()).

Source: the official Schema migration page.[5]

2. Config and logging, briefly

process.env.PORT is a string | undefined that you parse and check by hand, often at import time. A Config is a typed description of a setting. Yielding it reads from the current provider, which is process.env by default. A missing or malformed key fails with a typed ConfigError in E, so it doesn't crash your app at import time.[6]

const server = Effect.gen(function*() {
  const host   = yield* Config.String("HOST")
  const port   = yield* Config.Int("PORT")
  const apiKey = yield* Config.Redacted("API_KEY")   // prints as <redacted>
  return { host, port }
})   // Effect<{ host: string; port: number }, ConfigError>

// In tests, swap the source: it is just another Layer
const TestConfig = ConfigProvider.layer(
  ConfigProvider.fromUnknown({ HOST: "localhost", PORT: "8080", API_KEY: "s3cret" })
)
server.pipe(Effect.provide(TestConfig))

Notice the pattern from lesson 5 again: the config source is something you provide, so tests don't need to touch process.env. Logging is built in the same way. Effect.log, logInfo, logWarning and logError write structured lines, and Effect.annotateLogs({ orderId }) attaches fields to every line beneath it. Every Effect.fn("checkout") you wrote in lesson 3 also creates a tracing span named checkout. For new projects, the maintainers suggest exporting those spans with the lightweight OTLP modules in effect/observability.[1][7]

3. What else is in the box, and how stable is it?

Many libraries you'd normally install separately ship inside effect 4.0: @effect/platform, rpc, cli, ai and others were merged in.[8] For an adoption decision, the important question isn't “is it in the box?” but “what promise comes with it?” APIs tagged @stability unstable may break in minor releases. Untagged APIs follow strict semver.[8]

AreaImportStability in 4.0.0
Core: Effect, Layer, Context, Data, Schedule, Config, Logger"effect"Stable: no @stability tags in these modules
Streams, queues, state: Stream, Queue, PubSub, Ref"effect"Stable: no tags in Stream or Queue
Schema"effect"Mostly stable; about 120 advanced items are tagged
Time, caching: DateTime, Duration, Cron, Cache, ManagedRuntime"effect"Core package
HTTP client and server, schema-first HTTP APIseffect/http, effect/http-apiUnstable
SQL, AI providers, CLI, RPC, cluster, workfloweffect/sql, effect/ai, effect/cli, effect/rpc, …Unstable
OTLP export, Schema compilers (Model)effect/observability, effect/schemaUnstable
Runtime per platform (NodeRuntime.runMain, FileSystem)@effect/platform-node (also bun, deno, browser)Separate package, same version as effect

The full unstable list is: ai, cli, cluster, devtools, eventlog, http, http-api, jsonschema, observability, persistence, process, reactivity, rpc, schema, socket, sql, workflow and workers.[8] The 4.0 release post calls stabilising them the team's “first priority”.[9] Watch out for the similar names: Schema from "effect" is core, but the effect/schema subpath is a different, unstable module.

Adoption lens: add to your ledger

  • Pro: validation, typed config, structured logging and tracing come with the core package. You don't have to wire zod, dotenv and a logger together, and their failures land in the same E channel as everything else.
  • Pro: Schema.TaggedError and fromJsonString mean errors and payloads can cross process boundaries with one definition.
  • Cost: the parts many teams want first (HTTP, SQL, AI) are unstable in 4.0.0 and can break in minor releases. Pin versions, or keep your existing HTTP and DB libraries and wrap them with Effect.tryPromise.
  • Cost: Schema has its own large API, and v3 Schema tutorials are now misleading (see the v3 box above).

Check yourself

Answer from memory before scrolling back up.

1. You get a JSON string from a request body and want bad input as a typed error in E. What do you use?

  1. fromJsonString parses the string first, and decodeUnknownEffect puts any SchemaError in the error channel.
  2. The Sync variant throws on bad input, so the error never reaches E.
  3. A cast checks nothing at runtime. Bad input passes through silently.
  4. The input is a string, not an object, so the plain struct schema would reject every request.

2. What does typeof User.Type give you?

  1. .Type is the decoded type, the shape your code works with after decoding.
  2. typeof X.Type exists only at compile time. Validation comes from the decode functions.
  3. Nothing here produces JSON. .Type is a TypeScript type.
  4. That is typeof User.Encoded. .Type is the decoded side.

3. A program does yield* Config.Int("PORT"), but PORT isn't set. What happens?

  1. Missing config is an expected error in E, so you can catch it or provide a default with Config.withDefault.
  2. That is how process.env behaves. Config is typed, so it fails instead.
  3. A Config is read when the effect runs, not at import time, and the failure is typed.
  4. Config doesn't poll for values. A missing key is a ConfigError.

4. Why does @stability unstable on effect/http matter for your adoption verdict?

  1. Only untagged APIs get strict semver. Plan to pin versions or wrap your existing libraries.
  2. The tag is a compatibility promise. It says nothing about performance.
  3. Everything in effect is open source. The tags describe semver guarantees.
  4. The whole package supports TypeScript 5.9+, with 7 recommended. Stability is unrelated.
