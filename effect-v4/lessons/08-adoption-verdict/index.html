1. Adopt at the edge, not with a rewrite

Recall lesson 1: you run at the edge. In a new Effect app, the edge is main. In an existing app, any single function can be the edge. If an async function calls Effect.runPromise inside, it still returns a Promise, and its callers can't tell that anything changed. That lets you adopt Effect one function at a time.

Real handlers need services such as a database, a mailer or config. You don't want to rebuild those Layers on every request. A ManagedRuntime solves this. The maintainers' guide says it “bridges Effect programs with non-Effect code. Build one runtime from your application Layer, then use it anywhere you need imperative execution, like web handlers, framework hooks, worker queues, or legacy callback APIs.”[1]

Existing handler: plain TypeScript

const db = createPool(process.env.DB_URL) // global

export async function getUserHandler(req: Request) {
  try {
    const user = await db.findUser(Number(req.params.id))
    if (!user) return { status: 404, body: { error: "not found" } }
    return { status: 200, body: user }
  } catch (e) {
    // e: unknown. Which failures? Retry? Timeout?
    return { status: 500, body: { error: "internal" } }
  }
}

Same signature, Effect inside

const runtime = ManagedRuntime.make(UserRepo.layer) // built once

export async function getUserHandler(req: Request) {
  return runtime.runPromise(
    getUser(Number(req.params.id)).pipe(  // Effect<User, UserNotFound, UserRepo>
      Effect.timeout("2 seconds"),
      Effect.map((user) => ({ status: 200, body: user })),
      Effect.catchTag("UserNotFound", () =>
        Effect.succeed({ status: 404, body: { error: "not found" } }))
    )
  ) // a TimeoutError still rejects → your framework's usual 500
}
// on shutdown:
await runtime.dispose()

Three facts from the source are worth knowing.[2]

  • The Layer “is built lazily on first use and its context is cached for subsequent runs”, so every handler shares one connection pool.
  • Resources the Layer acquired “are released when dispose or disposeEffect is run”. Call await runtime.dispose() on shutdown.
  • “A runtime cannot be reused after disposal.”

The runtime has the same run* family you met in lesson 1 (runPromise, runPromiseExit, runSync, runFork). The difference is that the type checker now accepts Effects that need the runtime's services. The official example wires exactly this into Hono.[3]

This is the real answer to “Effect is all or nothing”. A pilot behind one function's signature can be reverted by swapping that function's body back.

2. The risk facts, with sources

A verdict needs facts, not vibes. Here is what the primary sources say as of 4.0.0:

FactWhat it means for you
4.x is LTS, with “at least three years of support”. Bug and security fixes run until at least Sept 2029.[4][5]Low risk that the core shifts under you during a multi-year project.
The core effect package has zero runtime dependencies.[5]Very little supply-chain surface.
Bundle: about 6–7 kB gzipped for a minimal program, about 15 kB with Schema. The blog and MIGRATION.md give slightly different figures.[6]Small, but not zero. It matters most for frontend bundles.
Stability tiers. Core modules (Effect, Layer, Context) follow strict semver. http, http-api, sql, ai, cli, rpc, cluster, workflow and others are @stability unstable: “may receive breaking changes in minor” releases.[6]Depending on the core is safe. Building centrally on unstable modules means planning for upgrade work.
Performance: v4 runs 4.57M tasks/s vs v3's 0.71M, and 50,000 fibers use 21.8 MB vs 157.5 MB. These are the project's own benchmarks.[5] The Myths page calls Effect “an app-level coordination library rather than a low-level operation wrapper”.[7]The overhead matters in tight numeric loops, not in I/O-bound services. Measure your own hot paths.
Churn in learning material. v3 tutorials, Stack Overflow answers and LLM output use renamed APIs. Some official pages still lag behind: the Myths page uses v3 names, and the blog footer links to the v3 API docs.A real onboarding cost. Your team needs to recognize v3 code on sight (next section).

Spotting v3 code: the tell-tale names

If a tutorial, blog post or LLM answer contains any of these, it was written for v3 or an early v4 beta. Translate it before you trust it.

  • Context.Tag, Effect.Tag, Effect.Service, MyService.Default: now Context.Service and static layer
  • ServiceMap.Service: v4 betas before beta.44, now Context.Service
  • Effect.catchAll / catchAllCause: now Effect.catch / catchCause
  • Either, Effect.either: now Result, Effect.result
  • Effect.fork / forkDaemon: now forkChild / forkDetach
  • Layer.scoped: now Layer.effect
  • Schedule.intersect / union: now Schedule.max([…]) / Schedule.min([…])
  • Schema.Literal("a", "b"), Schema.Union(A, B): now array arguments, Literals([…]), Union([…])
  • Effect.andThen(x => plainValue): in v4 it must return an Effect. Use Effect.map.

The full list is in the official MIGRATION.md and the course cheat sheet.

3. A decision framework

The official pitch is that TypeScript “says almost nothing about your programs: a function's signature doesn't tell you what can fail, what dependencies it needs, or whether it can be safely retried, timed out, or interrupted.”[8] That points to a test: how much of your pain lives in exactly those places? The table below is this course's heuristic, not an official rule. It combines that pitch with the costs you logged. Test it against your codebase and against practitioners in the Effect Discord.

SignalLeans adoptLeans skip
Kind of codeI/O-heavy backend services, workers, CLIsSmall scripts, UI-only components, mostly pure logic
Failure modesMany, and they need different handlingFew, and “log and 500” is fine
Dependencies & testsHand-rolled DI or module mocking hurtsFew dependencies, easy to test already
Retries, timeouts, concurrency, cancellationEverywhere, written by handRare
ObservabilityYou want spans and structured logs per operationNot a need
TeamTime to learn, and someone willing to champion itDeadline-bound, no learning budget, high turnover
Modules relied onMostly the stable coreCentral bets on unstable modules (http, sql, ai)

When the signals are mixed, the usual cheap middle path is a pilot. Pick one bounded piece with real failure modes, such as an outbound API integration that needs retries. Put it behind a ManagedRuntime and keep its signature unchanged. Decide your success criteria before you start.

Adoption lens: the final entries

  • Pro: you can adopt incrementally. One function at a time, behind unchanged signatures, so being wrong is cheap to undo.
  • Pro: the LTS guarantee and a zero-dependency core lower the long-term risk of the core.
  • Cost: the unstable modules and v3-era material mean ongoing upgrade and translation work. Budget for it if you use them.
  • Cost: the learning curve is the cost you can't buy your way out of. Your own experience with this course is evidence. Write it down.

Check yourself

Answer from memory before scrolling back up.

1. You want to try Effect in an existing Express app. What is the smallest safe first step?

  1. The handler keeps its signature, so the rest of the app is untouched and the change is easy to revert.
  2. That is a big-bang rewrite: costly to do and hard to undo. Running at the edge lets you start with one function.
  3. That swaps your whole stack for an unstable module before you have any evidence.
  4. Effect code and Promise code can coexist. runPromise is the bridge, so nothing has to convert first.

2. What does await runtime.dispose() do for a ManagedRuntime?

  1. It runs the Layer's finalizers. Afterwards the runtime can't be reused.
  2. It's the opposite: the Layer is built once, cached, and shared until you dispose.
  3. Disposing closes the runtime's whole scope, including the Layer's resources.
  4. Without dispose, the finalizers (closing pools, flushing logs) never run.

3. Your team's plan depends heavily on effect/http and effect/sql. What is the relevant risk?

  1. They are tagged @stability unstable. Only untagged core modules follow strict semver.
  2. They are new and actively being stabilised, not deprecated.
  3. They ship inside the open-source effect package.
  4. There are platform packages for Node, Bun, Deno and the browser.

4. An LLM gives you code that uses Effect.catchAll and Context.Tag. What do you conclude?

  1. catchAll became Effect.catch, and Context.Tag became Context.Service.
  2. Both were removed in v4, so this code won't compile against 4.0.0.
  3. Error handling is still there under new names: Effect.catch, catchTag, catchCause.
  4. Both are v3 names. The beta-era tell is ServiceMap.Service.
