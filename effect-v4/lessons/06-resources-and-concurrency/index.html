Resources, concurrency, timeouts and retries

The operational code you usually hand-write, available as operators.

Your win for this lesson

Guarantee that a resource is released however the program ends. Run work with a concurrency limit. Put a timeout and a retry policy on any Effect without touching its code.

In lesson 1 you saw that an Effect is a recipe, so you can wrap it before it runs. This lesson pays that off. Cleanup, parallelism, timeouts and retries are the parts of a backend that tend to be fragile and hand-written, and here each one becomes a single function you apply. These are also the strongest arguments in Effect's favour, so this lesson matters for your verdict.

Warm-up: recall from earlier lessons

Answer each one out loud or on paper before you open it.

What do the three channels in Effect<A, E, R> mean?

A is the success value, E the expected errors, and R the services it needs before it can run. E and R default to never. (Lesson 1)

What is the difference between an expected error and a defect?

An expected error is tracked in E and you recover from it with Effect.catchTag and friends. A defect is a bug or unexpected throw. It is not in E, only in the Cause. (Lesson 4)

An Effect has Database in its R channel. How do you make it runnable?

You provide a Database, either with Effect.provideService(Database, impl) or with Effect.provide(Database.layer). That removes it from R, and every runner needs R = never. (Lesson 5)

1. Resources that always get released

A database connection, a file handle or a lock must be released on every path: success, failure, and interruption, which means being cancelled from outside. In plain TypeScript you reach for try/finally. That works until the resource outlives one function, or until the caller abandons the work, for example after a timeout. At that point nothing tells the finally to run early.

Plain TypeScript: try/finally

const db = await openDb()
try {
  const cache = await openCache()
  try {
    await work(db, cache)
  } finally {
    await cache.close()   // you must nest by hand
  }
} finally {
  await db.close()
}
// If a caller "times out" with Promise.race,
// work() keeps running and nothing closes early.

Effect: acquireRelease + scoped

const openDb = Effect.acquireRelease(
  connect,                       // acquire
  (db, exit) => db.close         // release: always runs
)                                // Effect<Db, never, Scope>

const program = Effect.gen(function*() {
  const db = yield* openDb
  const cache = yield* openCache
  yield* work(db, cache)
})

Effect.scoped(program)  // closes cache, then db

Effect.acquireRelease(acquire, release) pairs the opening step with its cleanup, and puts a Scope into the requirements channel.[1] A Scope is the lifetime of your resources, and each release step is a finalizer registered in it. Effect.scoped(program) provides a fresh Scope and closes it when program ends.[2] Closing the Scope runs the finalizers in reverse order of acquisition, whatever the exit. The release function also receives the Exit, so it can tell a clean finish from a failure.

The Scope in R is the same idea as Database in R from lesson 5. The type won't let you run the program until something has taken responsibility for cleanup.

You already have one Scope for free. Inside Layer.effect, the layer's own scope is used, so a connection acquired while building a layer lives exactly as long as the layer.[3]

2. Concurrency with a limit, and with a safety net

Effect.all runs a list (or a struct) of effects. Effect.forEach(items, f) is the “map over a list” version. Both take a concurrency option, either a number or "unbounded". The default surprises most newcomers: “By default, if you don't specify any concurrency option, effects will run sequentially.”[4]

Plain TypeScript: Promise.all

// All 1,000 requests start at once: no limit.
const users = await Promise.all(ids.map(fetchUser))

// If one rejects, Promise.all rejects…
// …but the other 999 requests keep running.

Effect: forEach with concurrency

// At most 10 in flight. Results stay in input order.
const users = yield* Effect.forEach(ids, fetchUser, {
  concurrency: 10
})

// If one fails, the in-flight siblings are
// interrupted and their finalizers run.

The research for this course timed four 100ms tasks: about 400ms with the default, 200ms with concurrency: 2, and 100ms with "unbounded". That second guarantee is called structured concurrency. When one concurrent task fails, its siblings are interrupted rather than left running in the background. Effect.race works the same way and interrupts the loser.[5] A rejected Promise.all, by contrast, does not stop the other promises.[6]

Fibers, in one paragraph

Under the hood, each running effect is a fiber, a lightweight virtual thread managed by the Effect runtime.[7] Effect.all with concurrency creates fibers for you. You rarely need to touch them directly, but you can: Effect.forkChild starts one tied to the parent's lifetime, Fiber.join waits for its result, and Fiber.interrupt stops it.[8]

const program = Effect.gen(function*() {
  const ticker = yield* Effect.forkChild(tickForever)  // runs in the background
  const result = yield* Fiber.join(yield* Effect.forkChild(work))
  yield* Fiber.interrupt(ticker)                        // ticker's finalizers run
  return result
})

3. Timeouts and retries are just operators

Effect.timeout("2 seconds") adds Cause.TimeoutError to the error channel and interrupts the work when time runs out. The work is actually stopped, not just ignored.[9] Because it is a tagged error, you recover with the catchTag you learned in lesson 4:

const price = fetchPrice.pipe(
  Effect.timeout("2 seconds"),                        // Effect<number, FetchError | TimeoutError>
  Effect.catchTag("TimeoutError", () => cachedPrice)  // Effect<number, FetchError>
)

Effect.retry re-runs a failed effect according to a Schedule, a value that describes when to try again and when to give up.[10] You build schedules from small pieces and combine them. Schedule.max([a, b]) keeps going only while both keep going, and uses the longer delay.[11] That gives you the classic “back off exponentially, but at most N times” rule:

const policy = Schedule.max([
  Schedule.exponential("10 millis"),  // wait 10ms, 20ms, 40ms …
  Schedule.recurs(5)                  // … but stop after 5 retries
])

const robust = callApi.pipe(Effect.retry(policy))  // or Effect.retry({ times: 5 })

Notice that callApi never changed. The same policy value can wrap every outbound call in your codebase, and a test can swap in a faster one.

Reading older tutorials? v3 vs v4

  • Effect.fork → Effect.forkChild, and Effect.forkDaemon → Effect.forkDetach.[8]
  • Fibers are no longer Effects. Instead of yield* fiber, write Fiber.join(fiber). Ref and Deferred changed the same way.[12]
  • Schedule.intersect / both → Schedule.max([…]), union / either → Schedule.min([…]), and andThen → Schedule.concat.[11]
  • Layer.scoped → Layer.effect, which now handles scoped resources itself.
  • Effect.timeoutFail / timeoutTo → Effect.timeoutOrElse, and built-in *Exception errors are now *Error (TimeoutError).

Adoption lens: add to your ledger

  • Pro: cleanup is guaranteed on success, failure and interruption, and nesting more resources doesn't add more try/finally blocks.
  • Pro: cancellation really stops work. Timeouts, races and failed siblings interrupt the fibers involved, which Promises cannot do.
  • Pro: concurrency limits, retry and timeout policies are one-line values you can reuse and test, not loops you rewrite per call site.
  • Cost: more concepts to learn: Scope, finalizers, fibers, Schedule. Interruption semantics take time to build intuition for.
  • Cost: the sequential default is safe but easy to forget. Code that “looks parallel” may not be until you add concurrency.

Check yourself

Answer from memory before scrolling back up.

1. A program opens db, then cache, both with acquireRelease, and then fails. It is run with Effect.scoped. What happens?

  1. Finalizers run on every exit, in reverse order of acquisition: cache, then db.
  2. Both close, but in reverse order, like nested try/finally blocks: the last one opened closes first.
  3. Release runs on success, failure and interruption. That is the whole point of acquireRelease.
  4. Every finalizer registered in the Scope runs when the Scope closes.

2. Effect.all([a, b, c, d]) with no options. How do the four effects run?

  1. Without a concurrency option, Effect.all is sequential. Add { concurrency: n } to overlap them.
  2. That is a common assumption, but it's wrong. Concurrency is opt-in with the concurrency option.
  3. There is no hidden limit. The default is fully sequential.
  4. The order is deterministic: they run in sequence, and results come back in input order.

3. Effect.all([slow, failing], { concurrency: "unbounded" }), where failing fails after 50ms and slow needs 1 second. What happens to slow?

  1. That is structured concurrency: a failing sibling interrupts the others, and cleanup still runs.
  2. That is what Promise.all does. Effect interrupts the sibling instead.
  3. The whole thing fails after about 50ms. It doesn't wait for slow.
  4. An interrupted fiber does not resume. Running the Effect again starts the recipe from scratch.

4. When does Effect.retry(Schedule.max([Schedule.exponential("10 millis"), Schedule.recurs(5)])) stop retrying a call that keeps failing?

  1. max continues only while both schedules continue. recurs(5) stops after 5 retries, and exponential makes each wait longer.
  2. On its own, yes. Combined with recurs(5) through max, it stops when recurs stops.
  3. "10 millis" is the first delay, not a total time budget.
  4. Five retries is right, but exponential doubles the delay each time: 10, 20, 40 …
