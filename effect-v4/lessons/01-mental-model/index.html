An Effect is a recipe, not a running task

The one idea everything else in Effect is built on.

Your win for this lesson

Read any Effect<A, E, R> type and say what it succeeds with, how it can fail, and what it needs. Explain why nothing happens until you run it.

You are here to decide whether Effect is worth adopting. To judge that fairly, you first need to know what an Effect actually is. Typed errors, dependency injection, retries and cancellation all come from the one idea in this lesson. If this idea clicks, the rest of the course is mostly vocabulary.

1. A Promise is already running

In plain TypeScript, a Promise starts working the moment you create it. It represents a task that is already in flight. An Effect is the opposite. The docs describe it as “a description of a workflow or operation that is lazily executed … when you create an Effect, it doesn't run immediately”.[1]

Plain TypeScript: eager

const promise = new Promise<number>((resolve) => {
  console.log("runs immediately")
  resolve(1)
})
// "runs immediately" is already printed.
// You can't run it again, and you can't stop it.

Effect: lazy

const effect = Effect.sync(() => {
  console.log("runs only when run")
  return 1
})
// Nothing printed yet. It is a value.

Effect.runSync(effect) // prints, returns 1
Effect.runSync(effect) // prints again: a reusable recipe

Think of the difference between a recipe and a meal on the stove. A Promise is the meal: it is cooking right now. An Effect is the recipe. Writing it down cooks nothing. You can hand it to someone else, add a step (“if it burns, try once more”), or cook it twice. Effects are immutable values that “do not perform any actions themselves”; the Effect runtime executes them.[1]

This is why Effect can offer retry and timeout as plain functions. You can only retry something you still have the recipe for, and a Promise has already used its recipe up.

2. The type tells the whole story: Effect<A, E, R>

An Effect's type has three parameters, called channels.[1]

A
Success channel
The value it produces if it succeeds.
E
Error channel
The expected errors it can fail with. never means it can't fail.
R
Requirements channel
The services it needs before it can run. never means it needs nothing.

E and R both default to never. In the source, the declaration is interface Effect<out A, out E = never, out R = never>.[2] So Effect.Effect<number> reads as “produces a number, can't fail, needs nothing.” Here is how the channels fill in as you build things up:

const one  = Effect.succeed(1)    // Effect<number, never, never>
const oops = Effect.fail("boom")  // Effect<never, string, never>

const time = Effect.gen(function*() {   // Effect<number, never, Clock>
  const clock = yield* Clock            // ← asking for a service puts Clock in R
  return yield* clock.now
})

Compare that with a plain function getTime(): Promise<number>. Its signature hides two things: whether it can throw, and that it secretly reads a global clock. The Effect version puts both into the type.

The docs offer a rough mental picture: an Effect is like a function (context: Context<R>) => E | A. You give it the services it needs, and you get back either an error or a value. The docs then add, “However, effects are not actually functions.”[1] Use the picture to build intuition, not as a definition.

3. Run it once, at the edge

A recipe does nothing until someone cooks it. In Effect, you do that with one of the run* functions.[3] Ideally you call one only once, at your program's entry point: in main, an HTTP handler, or a test. Everything inside stays a description. This course calls that running at the edge.

FunctionGives youOn failure
Effect.runSync(e)the value, synchronouslythrows (and throws if e is async)
Effect.runPromise(e)a Promise of the valuerejects with the error
Effect.runSyncExit(e) / runPromiseExitan Exit: success or failure as datanever throws
NodeRuntime.runMain(e)a real Node app's entry pointlogs, sets exit code, handles Ctrl-C

Every runner requires R = never. Try to run time from above and you get a compile error, because nobody has supplied a Clock yet. You fix that by providing one, which removes it from R:

// Effect.runSync(time)   ← type error: Clock is still required

const runnable = time.pipe(
  Effect.provideService(Clock, { now: Effect.succeed(42) })
)                                  // Effect<number, never, never>

Effect.runSync(runnable)           // 42

That snippet is dependency injection checked by the compiler, in a few lines. Lesson 5 covers it properly. For now, just notice that the type would not let you forget to supply the dependency.

Reading older tutorials? v3 vs v4

In v3, runPromise rejected with a FiberFailure wrapper. In v4 it rejects with your raw error.[4] The type helper Effect.Effect.Context<T> is now Effect.Services<T>. The mental model itself has not changed.

Adoption lens: add to your ledger

  • Pro: a signature tells the truth. You can see what a function returns, how it fails and what it depends on without reading its body.
  • Pro: because programs are values, you can wrap them (retry, timeout, provide a test double) without changing them.
  • Cost: your code now has two worlds, Effect values and ordinary values, and you cross between them with run* at the edges. Keep this cost in mind; lesson 8 comes back to it.

Check yourself

Answer from memory before scrolling back up. Effortful recall is what makes this stick.

1. const e = Effect.sync(() => console.log("hi")). When is “hi” printed?

  1. Effect.sync stores the function. Every run calls it again.
  2. That is what a Promise does. An Effect is lazy, so defining it runs nothing.
  3. You can't await an Effect directly, and it isn't cached. Each run calls the function again.
  4. Sync effects run fine when you run them, for example with Effect.runSync.

2. What does Effect.Effect<User, NotFound, Database> tell you?

  1. The channels are always in this order: A (success), E (error), R (requirements).
  2. That reads the channels backwards. A comes first: User is the success value.
  3. The second slot is E, the error channel. R is only the third slot.
  4. The first slot is the success value, so this has A and E swapped.

3. time has type Effect<number, never, Clock>. Why does Effect.runSync(time) fail to compile?

  1. Every runner needs R = never. Provide a Clock first.
  2. runSync accepts failing effects; it throws the error when they fail. The problem here is R.
  3. Running an async effect with runSync fails at runtime, not at compile time. The compile error is about R.
  4. Effect.gen builds an ordinary Effect, and any runner works on it once R is never.

4. In a well-structured Effect app, where does runPromise (or runMain) usually appear?

  1. Everything inside stays a composable description, and the run happens at the boundary.
  2. That runs effects too early and throws away the benefits: you can no longer retry, time out or provide them.
  3. Inside Effect.gen, yield* already gives you the value. No run is needed.
  4. Production code runs effects too, once, at its entry point.
